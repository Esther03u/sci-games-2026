## 1. ปัญหาที่ต้องแก้ เรียงตามความสำคัญ

### P0 — บล็อกการใช้งานจริง

1. **ผู้ชนะไม่เลื่อนเข้ารอบชิงอัตโนมัติ** — `scripts/seed-matches.mjs` ไม่เขียน `next_match_id` / `next_match_slot` / `loser_next_match_id` / `loser_next_match_slot` ลง DB (เขียนแค่ sport/teams/date/time/venue/round/category/match_number/status) ทั้งที่ `handbook.js` มีข้อมูลนี้ครบแล้วและ trigger ใน migration 002 รออยู่ → **ฟีเจอร์ bracket ที่เพิ่งทำจะไม่ทำงานกับข้อมูลจริง** กรรมการจะต้องกรอกทีมรอบชิงเองทุกคู่
2. **DB ยังเป็นชุดข้อมูลเก่า** — 20 คู่ของรอบชิงที่ 1/ชิงที่ 3 มีชื่อทีม "ปลอม" อยู่ (เช่น ชิงชนะเลิศฟุตซอลหญิง = ม่วง vs แดง) ซึ่งจะแสดงผิดบนหน้าผู้ชมทันทีที่เปิดงาน
3. **ข้อมูลทดสอบค้างใน DB** — 2 แมตช์ฟุตซอลสถานะ `finished` (2-2, 2-1), `score_events` 11 แถว, PIN ชื่อ `song` ยังเปิดใช้งาน
4. **เวลาเซปักตะกร้อ 3 คู่ผิด** และทำให้คู่ 4 ชนกับคู่ 5 ที่ 19.30
5. **กติกาคะแนนผิด** — ตะกร้อ 21 (ที่ถูกคือ 15/8), เปตองตั้งเป็นระบบเซต (ที่ถูกคือเกมเดียวถึง 11, ชิงชนะเลิศ 13)

### P1 — ควรแก้ก่อนงาน

6. **สูจิบัตรบนเว็บเป็นคนละฉบับกับ `final/`**
7. **โควตานักกีฬาไม่แยกประเภท** (ดูตารางข้อ 0) — `registrations` ไม่มีคอลัมน์ประเภท จึงนับรวม ชาย+หญิง+ผสม เป็นก้อนเดียว
8. **สนามเปตอง** — `matches` ไม่มีคอลัมน์ `court` แต่ UI (`MatchCard`, `MatchDetailModal`) อ้าง `match.court`; seeder จึงยัดค่า court ลงช่อง `venue` ทำให้ข้อความกลายเป็น "สนามเปตอง สนาม 1 ม.ราชภัฏภูเก็ต" (ปัจจุบันใน DB เป็น "สนาม 1" เฉย ๆ ซึ่งไม่บอกว่าเป็นสนามเปตอง)
9. **ฟุตซอล/บาสเกตบอลเสมอไม่ได้ตามกติกา** (จุดโทษ / ต่อเวลา) แต่ระบบปล่อยให้กดจบแบบเสมอ และ `team_standings` ให้ทีมละ 1 แต้ม — ในทัวร์นาเมนต์แพ้คัดออกไม่ควรมีผลเสมอเลย
10. **ชื่อประเภทของเปตองไม่ตรงกับกีฬาอื่น** — เปตองใช้ "คู่ชาย/คู่หญิง/คู่ผสม" ส่วนกีฬาอื่นใช้ "ชาย/หญิง" (สูจิบัตรเขียน ชาย/หญิง/ผสม ทั้งหมด) ตัวกรองหน้าเว็บยังใช้ได้เพราะจับแบบ substring แต่ป้ายบนการ์ดจะไม่สม่ำเสมอ

### P2 — ถ้ามีเวลา

11. **กำหนดการวันอาทิตย์ยังไม่มีในระบบ** — ลงทะเบียน 08.00, พิธีเปิด 09.00, วอลเลย์บอลยักษ์ 09.45, พักเที่ยง, ประกาศผล + พิธีปิด 14.30–16.30 (ตอนนี้ `/schedule` แสดงเฉพาะแมตช์)

## 2. ลำดับการลงมือ

> ทุกขั้นจบด้วย `npm run build` + `npm test` + `npm run lint`; ขั้นที่แตะ DB ต้องผ่าน `bash supabase/tests/run-local.sh`

### ขั้น 1 — แก้ข้อมูลต้นทางใน repo (ไม่กระทบของจริง)
- `src/data/handbook.js`: แก้เวลาเซปักตะกร้อคู่ 2, 3, 4 → 18:00, 18:30, 19:00
- (ถ้าเลือกทำข้อ 10) เปลี่ยนประเภทเปตองเป็น ชาย/หญิง/ผสม ให้ตรงสูจิบัตร
- เพิ่ม unit test ที่ตรวจว่า **ทุกคู่ในสนามเดียวกันไม่ชนเวลากัน** และจำนวนคู่ต่อกีฬา = 8/8/8/8/12 กันพลาดซ้ำ

### ขั้น 2 — ทำให้ seeder เขียน bracket links (แก้ P0-1)
- หลัง `insert` ให้ทำรอบที่สอง: map `handbook id → uuid` ที่เพิ่ง insert แล้ว `UPDATE` ใส่ `next_match_id/slot`, `loser_next_match_id/slot`
- เพิ่มธง `--force` สำหรับลบแมตช์ที่มี link แล้ว seed ใหม่ (ตอนนี้ `--replace` เว้นแถวที่มี link ไว้ เพื่อกัน bracket ที่ generate เอง)
- ตรวจด้วย `--dry` ว่าได้ 44 คู่ + 20 ลิงก์ (ผู้ชนะ 20 / ผู้แพ้ 20 จาก 20 คู่รอบแรก… นับจริง: คู่รอบแรก 24 คู่ × 2 ลิงก์)

### ขั้น 3 — migration 009: กติกาและโควตาให้ตรงสูจิบัตร
```sql
-- ตะกร้อ 15 (เซตตัดสิน 8), เปตองเป็นเกมเดียวถึง 11 (ชิงชนะเลิศ 13)
UPDATE sports SET points_per_set = 15 WHERE name = 'เซปักตะกร้อ';
UPDATE sports SET scoring_type = 'points', sets_to_win = 1, points_per_set = 11 WHERE name = 'เปตอง';
-- โควตารวมทุกประเภทต่อสี (ดูตารางข้อ 0)
UPDATE sports SET max_players_per_team = 28 WHERE name = 'ฟุตซอล';   -- 14 × ชาย/หญิง
...
```
- **ตัดสินใจ**: เซตตัดสิน (วอลเลย์ 15 / ตะกร้อ 8) และคะแนนชิงชนะเลิศเปตอง 13 — schema เก็บค่าเดียวต่อกีฬา มี 3 ทาง
  - (ก) ปล่อยให้กรรมการกดจบเซต/จบแมตช์เอง (ระบบไม่บังคับคะแนน) — **เร็วที่สุด ไม่แตะ schema** และตรงกับที่ระบบทำอยู่แล้ววันนี้
  - (ข) เพิ่ม `deciding_set_points` + `final_points` ใน `sports` แล้วให้ฟังก์ชัน `finish_set`/`finish_match` ใช้
  - (ค) ใส่เป็นข้อความเตือนบนหน้าจอกรรมการเฉย ๆ
- โควตาแยกประเภท (P1-7) มี 2 ทาง: (ก) ตั้งค่ารวมตามตารางข้างบน — พอสำหรับปีนี้ (ข) เพิ่ม `category` ใน `registrations` + ฟอร์มสมัคร + validation — ถูกต้องกว่าแต่กระทบหลายจุด

### ขั้น 4 — ล้างข้อมูลทดสอบแล้ว seed ของจริง (ทำตอนใกล้วันงาน)
1. ลบ `score_events` 11 แถว + คืน 2 แมตช์ที่ finished เป็น `upcoming`
2. ปิด/ลบ PIN `song` แล้วสร้าง PIN จริงรายกีฬา–รายสนาม
3. `npm run seed:matches -- --dry` ตรวจก่อน → `--replace` (หรือ `--force`) แล้วตรวจ 44 คู่ + ลิงก์ครบ
4. ตรวจหน้าเว็บ: `/schedule` 44 คู่, `/results` แสดง "รอผลการแข่งขัน" ในรอบชิง, `/live` (ล็อกอิน) เห็นครบ

### ขั้น 5 — เอกสารและรายละเอียดหน้าเว็บ
- คัดลอก `final/สูจิบัตร69 (3).pdf` → `public/docs/sci-games-2026-handbook.pdf` (กำหนดการตรงอยู่แล้ว ไม่ต้องแตะ)
- (P2) เพิ่มกำหนดการวันอาทิตย์เป็นรายการพิเศษในหน้า `/schedule`
- อัปเดต `Handoff.md` + `docs/runbook-matchday.md` แล้ว push (ต้องให้เพื่อน push ตามเพื่อ deploy)

## 3. ความเสี่ยงและข้อควรระวัง

- **ลำดับสำคัญ**: ต้องแก้ seeder (ขั้น 2) ให้เสร็จ *ก่อน* seed จริง (ขั้น 4) ไม่งั้นต้อง seed ซ้ำ และการ seed ซ้ำหลังมี link ต้องใช้ `--force`
- **อย่า seed ทับหลังเริ่มแข่ง** — จะลบแมตช์ที่มีคะแนนแล้ว; ถ้าต้องแก้ตารางกลางงานให้แก้ทีละคู่ที่ `/admin/matches`
- migration 009 เป็นแค่ `UPDATE` ค่าคงที่ ปลอดภัยและ idempotent แต่ต้องรันบน Supabase จริงเอง (commit ของ AI ไม่ deploy เอง — ดู Handoff §3)
- ถ้าเลือกแก้ประเภทเปตอง (P1-10) ต้อง seed ใหม่ทั้งชุด เพราะ `category` ฝังอยู่ในแถว

## 4. สิ่งที่ยังต้องให้ผู้ใช้ตัดสินใจ

1. เซตตัดสิน/คะแนนรอบชิง (ข้อ 3 ขั้น 3) — เลือก (ก) ปล่อยกรรมการคุม, (ข) เพิ่มคอลัมน์, หรือ (ค) เตือนบนหน้าจอ
2. โควตาสมัคร — ตั้งค่ารวม หรือแยกประเภทจริง (หรือไม่ต้องแตะ ถ้าปิดรับสมัครผ่านเว็บแล้ว)
3. ชื่อประเภทเปตอง — คงเป็น "คู่ชาย/คู่หญิง/คู่ผสม" หรือเปลี่ยนเป็น "ชาย/หญิง/ผสม" ตามสูจิบัตร
4. กติกาเรื่องเสมอของฟุตซอล/บาส — ให้ระบบเตือน/ห้ามกดจบเมื่อคะแนนเท่ากันไหม
5. กำหนดการวันอาทิตย์ (พิธีเปิด/ปิด) — ต้องการให้แสดงบนเว็บไหม
